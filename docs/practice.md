# PickLoop 직접 실습

**판단할 문제는 경로 차단과 흡착 실패에 같은 높이의 재시도 경로가 필요한가입니다.** 한 조건의 성공을 재현하고, 운반 높이 규칙 한 곳을 바꾼 뒤 그 변경을 채택할지 결정해 보세요. 결과물이 되는 세 가지는 본인이 실행한 로그, 직접 만든 코드 차이, 그 둘을 근거로 쓴 판단입니다.

## 1. Codespaces에서 원래 동작 실행

운반 높이 규칙은 현재 `main`에 반영돼 있습니다. [PR #1 전후 원본](experiments/retry-height/)으로 결과를 먼저 볼 수 있습니다. 같은 변경을 처음부터 실습하려면 Codespace 터미널에서 프로젝트 루트 기준으로 아래 명령을 실행해 변경 전 소스를 별도 경로에 여세요. 기존 작업은 현재 브랜치에 남습니다.

```bash
git fetch origin main
git worktree add --detach ../pickloop-height-baseline cd951bd200b779e8ff9c04faecb999c4d5624144
cd ../pickloop-height-baseline
```

이 경로의 `src/pickloop/engine.py`를 편집하고 아래 명령도 같은 경로에서 실행합니다.

```bash
python lab.py run my-before
```

개발 seed 200에서 다섯 작업을 새로 실행합니다. 화면의 각 행은 시뮬레이션 시각, 시도 번호, 이벤트 순서입니다. 먼저 `path_blocked / reobserve`와 `path_blocked / recovery`의 **첫 실패 원인, 다음 시도 번호, 최종 상태**를 각자 적으세요. `my-before/<run_id>/events.jsonl`에는 실패한 단계와 충돌 검사에서 발견한 물체 이름도 있습니다. `PATH_BLOCKED`는 계획 검사에서 길이 막혔다는 뜻입니다. 실제로 부딪혔는지는 `result.json`의 `metrics.collisions`에서 확인합니다.

실행이 끝나면 `cp RECORD.md my-notes.md`로 본인의 기록지를 만드세요. 이미 쓰던 기록지가 있으면 그대로 이어 쓰세요. 같은 이름의 실행 폴더는 보존되므로 다시 실행할 때는 새 이름을 씁니다.

## 2. 수정하기 전에 예측

`src/pickloop/engine.py`에서 `Controller.transport_height`를 찾으세요. 변경 전 `recovery` 정책은 두 번째 시도부터 운반·복귀 높이를 0.30m에서 0.40m로 올립니다. 이 값은 `transport()`와 `release()`가 함께 씁니다. 물체를 계속 잡고 있으면 `plan()`을 건너뛰므로 모든 운반 높이가 `PLAN_READY` 이벤트에 나타나는 것은 아닙니다.

- 보정 오차로 **흡착 전** 실패했다면, 재관측으로 얻는 새 목표 좌표와 더 높은 **운반 경로** 중 어느 쪽이 실패 원인에 대응할까요?
- 이미 물체를 잡은 상태에서 **운반 경로**가 막혔다면, 목표 좌표만 다시 읽는 것으로 길이 열릴까요?
- 어떤 동작이 빨라질 것으로 예상하나요? 어떤 결과가 하나라도 나오면 수정을 철회할 건가요?

기록지에 예상 결과와 철회 기준을 먼저 적으세요. 예를 들어 경로 차단을 통과하던 작업이 보류로 끝나거나 충돌·낙하·오배치가 늘면 시간 절약을 이유로 채택하기 어렵습니다.

## 3. 한 곳을 직접 수정

첫 실험으로 **직전 실패 원인이 경로 차단일 때만 높은 경로를 사용**하는 규칙을 시험해 보세요. 실습 사본의 `Controller.transport_height`만 수정합니다.

1. 현재 `recovery` 정책인지, 재시도 중인지 검사하는 두 조건을 찾습니다.
2. `self.last_error`에 직전 실패가 저장됩니다. 오류가 있고 `self.last_error.code == 'PATH_BLOCKED'`인지 조건에 추가해 보세요. 첫 시도에는 오류가 없을 수 있습니다.
3. 조건을 만족하면 0.40m, 그 밖에는 0.30m를 반환하도록 저장합니다. 시도 한도, 압력 기준, 경로 충돌 검사는 두 실험에서 같아야 합니다.

판단에 쓸 정보는 로봇이 실행 중 받은 오류 코드입니다. 실험기가 아는 장애 시나리오 이름을 코드에 넣으면 미리 정답을 알려준 비교가 됩니다.

```bash
python lab.py run my-after
python lab.py compare my-before my-after
```

`compare`는 조건 ID와 정책, 모델 해시를 대조하고 `my-after/engine.diff`를 생성합니다. 자신의 코드 한 곳만 바뀌었는지 diff를 읽으세요. 각 조건의 위 행은 변경 전, 아래 행은 변경 후입니다. 경과 시간은 작업 시작부터 종료까지의 시뮬레이션 시간입니다. 로그의 이벤트 시각은 셀 초기화 시간을 포함합니다.

## 4. 결과를 읽고 결정

| 확인할 작업 | 판단할 내용 |
|---|---|
| 경로 차단 / 재관측만 | 두 번 더 시도해도 동일 경로가 막히는지, 물체를 들고 보류한다면 밸브에 어떤 결정을 내렸는지 확인합니다. |
| 경로 차단 / 재관측·재계획 | 높은 경로가 필요한 작업의 성공을 유지했는지 확인합니다. |
| 보정 오차 / 재관측·재계획 | 재관측 후 올바른 품목 배치가 유지됐는지, 경로 높이를 원래대로 썼을 때 시간이 어떻게 달라졌는지 확인합니다. |
| 정상 / 재관측·재계획 | 첫 시도 작업에도 영향이 생겼는지 확인합니다. |
| 지속 흡착 실패 / 재관측·재계획 | 마지막 `STATE_FAILED`, `RETRY_EXHAUSTED`, `HOLD_POLICY`, `TERMINAL`을 원문에서 차례로 찾으세요. 완료율 대신 재시도 횟수, 분리·압력 상태, 밸브 결정이 이 상황에 맞는지 설명하세요. |

모든 안전 수치가 같아도 한 seed에서의 시간 절약만으로 전체 시스템 개선을 확정하기는 어렵습니다. 특히 높이를 바꾼 뒤 다른 종류의 실패가 연속으로 나면 ‘직전 오류’만 기억하는 규칙은 이전 장애물을 잊을 수 있습니다. 다음 검증으로 어떤 연속 실패를 만들 것인지 한 가지 적으세요. 다른 개발 seed를 비교할 때는 원래 코드를 복원해 전 실험부터 다시 실행한 뒤 같은 seed로 후 실험을 실행합니다. `run`은 `--seed 201`처럼 200~209를 받습니다.

실행이 다르게 끝나면 그 run_id를 보관하고 첫 번째로 달라진 이벤트를 찾으세요. `DEVICE_UNCERTAIN`이면 TCP 명령 결과를 확인하지 못한 기록입니다. 원인이 확인되기 전에는 경로 높이의 효과로 해석할 수 없습니다. 중단된 배치가 남아 있으면 새 폴더에 다시 실행합니다.

## 5. 내 판단을 말해 보기

- **공정한 비교** — 1회 기준 정책과 최대 3회 복구 정책을 비교하면 무엇이 섞이나요? 이번에는 정책의 어떤 조건을 고정했나요?
- **성공 기준** — `Controller.verify`에서 카메라 두 시점과 장치 상태를 왜 함께 보나요? 자기 실행의 `result.json`에서 `verified_by_vision`과 `verified_by_truth` 값을 찾아 설명해 보세요.
- **보류 판단** — `HOLD_POLICY`의 `RETAIN`은 출력을 쓰지 않았다는 의미입니다. `OFF_CONFIRMED`는 OFF 명령과 상태를 확인한 경우입니다. 물체가 붙어 있거나 응답이 불확실한데 밸브를 끄면 어떤 문제가 생길까요?

면접에서는 기록지를 보면서 **관측한 문제 → 자신이 바꾼 조건 → 같은 조건에서 나온 두 결과 → 채택·보류 판단** 순서로 말해 보세요. 직접 수행하기 전에는 기록지의 실행자와 결과를 비워 둡니다.
